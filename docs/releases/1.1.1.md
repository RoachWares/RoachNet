# RoachNet 1.1.1

Release date: not yet released
Version/build: 1.1.1 / 111
Platform: Apple Silicon Mac, macOS 14 or later
Installer: `RoachNet-Setup-macOS.dmg` (ad-hoc signed, not Apple-notarized — see "Opening the installer" below)
Companion: RoachNet-iOS 0.3.1 (unchanged, separate release)

RoachNet 1.1.1 is a security maintenance release for 1.1.0. It fixes one data-loss problem in downloads, adds related download safeguards, and fixes how Setup recovers from an upgrade that was cut off. Nothing else in the app changes. Everyone on 1.0.6, 1.0.7 or 1.1.0 should update.

## Security fix

**A malformed catalog download could delete RoachNet's storage folder.**

- **Severity:** High (preliminary): potential unintended local data deletion through malformed download descriptors. What it takes to trigger differs between the affected releases (below).
- **Affected versions:** RoachNet 1.0.6, 1.0.7 and 1.1.0 for macOS.
- **Not affected:** 1.0.5 and earlier, and the RoachNet iOS companion.
- **What happened:** when an entry in RoachNet's download catalog gave a file name that refers to a folder, RoachNet treated that folder as the download's file. When the download then failed, or when RoachNet moved the finished file into place, it removed that folder and everything in it.
  - For a knowledge (ZIM) download, that folder was the whole storage folder: the Vault, downloaded knowledge and maps, local models and RoachClaw's data.
  - Deleted files did not go to the Trash.
- **What it took:**
  - **1.0.7 and 1.1.0:** the download had to come from RoachNet's catalog address, and the catalog entry had to carry such a name. RoachNet's published catalog doesn't carry one. So this needed control over what the catalog serves.
  - **1.0.6:** it followed download descriptors from any web address, so starting a download from an untrusted link was enough.
- **What changed:**
  - A download whose name refers to a folder gets a generated name instead.
  - A download always lands directly inside its destination folder.
  - A download's cleanup removes only files, never a folder.
  - A failed, interrupted, cancelled or mismatched download leaves an existing file at its path in place. The one exception: when a RoachSpeech pack's install step fails, the pack's earlier downloaded archive isn't kept; the installed pack is.
  - Regression tests cover each case.

## Related download safeguards

Each keeps a download from writing into, or replacing, a file it doesn't own:

- A link at a download's partial file, symbolic or hard, is removed, never written through.
- One download writes a given file at a time, until its work has stopped, a cancelled one included. Names that differ only in case or Unicode normalization count as one file.
- A download from the download catalog or a web address can't be given the name of another download's partial file or resume marker.
- A cancel that stops a download leaves the file that was there. Once the new file is taking its place, a cancel is refused.

What changes with them:

- A second request for a file that is already downloading from another source is refused instead of sharing its partial file.
- An install already running can't be cancelled.
- A collection queues each of its items on its own, so one that can't be queued doesn't stop the rest.

## Setup: recovering from an interrupted upgrade

**An upgrade cut off part-way could bring RoachNet back empty.** This is in 1.0.6, 1.0.7 and 1.1.0. No data was deleted.

- **What happened:** an upgrade moves the old install aside before it puts the new one in place. When it was cut off after that step, Setup's own log (or, with Homebrew, the cask putting its Setup app back) recreated `~/RoachNet` before Setup looked for the install it had moved aside, so Setup kept that backup instead of restoring it. RoachNet then opened empty, and the person's data stayed in `~/RoachNet.backup-<time>`.
- **What changed:**
  - Setup writes its log beside the installer settings (`~/Library/Application Support/roachnet/setup.log`), not inside the install.
  - Two copies of 1.1.1's Setup no longer run at once: when the Setup app and a Homebrew install overlap, the second one stops and says why. If Setup can't open its lock file (one another user left, say), it stops and names the file to remove. Older Setups don't take part in this, and where it can't work (on a file system without file locks, for example), Setup goes ahead as before.
  - Setup looks at what it finds before it writes anything in `~/RoachNet`. When `~/RoachNet` is missing or holds only Setup's own files, Setup puts back the newest of its backups that holds more than that.
  - Only Setup's own folders count: its `~/RoachNet.backup-<time>` backups and its unfinished `~/RoachNet.staging-<id>` folders. A folder named any other way is left alone. (Earlier versions removed anything beside the install whose name began with `RoachNet.staging-`.)
  - When a backup can't be put back, or Setup can't tell whether one is there (a folder it can't read, or a link to a drive that isn't connected), Setup stops before installing anything, says what it found and what to do, and names the backup when it found one, instead of opening RoachNet empty.
  - With Homebrew, when Setup stops this way, Homebrew keeps the new Setup app instead of putting the previous version back, and reports success even though RoachNet isn't installed or updated yet. Do what Setup's message says, then run `brew reinstall --cask roachnet`.
  - For scripted installs, `roachnet-runtime --install` exits with 75 when another Setup is running or its lock file can't be opened, and with 65 when Setup stopped before installing.
  - Recovery removes only Setup's own unfinished staging folders and the older copy of the Setup app it replaces. Anything else it has to clear from `~/RoachNet` is moved aside and kept, and a folder it can't read is treated as one that may hold your data.
  - Folder names are matched the way the install's volume matches them.
  - Regression tests cover recovery, the lock and the stops. The release's install lanes run an interrupted upgrade through the Setup app's backend and through the command the Homebrew cask runs, and check that Setup stops when a backup can't be read and when another Setup is running.

## Other changes

Three build-side corrections, none of which changes what ships:

- A test-only correction lets release qualification run the Metal kernel host check again; no kernel or app code changed.
- A fresh import of the RoachVoice Chatterbox pack writes the pack its recorded digests describe again, so the release build can verify it; the published pack doesn't change.
- A test-only correction keeps a Claude stream trace test from failing when two turns start in the same millisecond.

## Opening the installer

This build is **ad-hoc signed and not Apple-notarized**, like 1.1.0. On first launch macOS says RoachNet Setup cannot be verified: open System Settings › Privacy & Security and choose **Open Anyway** for RoachNet Setup. Verify the download first:

```sh
shasum -a 256 -c RoachNet-Setup-macOS.dmg.sha256
```

Homebrew: `brew tap --force RoachWares/roachnet && brew install --cask roachnet`. Already installed with Homebrew: `brew upgrade --cask roachnet`.

## Upgrade, rollback and removal

- **Before you update:** keep a current backup of `~/RoachNet/storage` (Time Machine works). Until you update, leave RoachNet's catalog address at its default and don't start downloads from links you don't trust.
- **Upgrade:** quit RoachNet and run Setup over the existing install. `~/RoachNet/storage` (Vault, settings, models) is kept.
- **Rollback:** 1.1.0 and 1.1.1 use the same storage format, but going back to 1.1.0 brings both problems back.
- **If an upgrade was cut off and RoachNet won't open because `~/RoachNet/app/RoachNet.app` is missing:** run 1.1.1's Setup. It puts your install back. With Homebrew, run `brew reinstall --cask roachnet`: `brew upgrade` stops in this case, because the Setup app it looks for is inside the backup.
- **If RoachNet opened empty after an earlier upgrade:** your data is still in a `~/RoachNet.backup-<time>` folder beside the install (`~` is your home folder). Setup won't put it back on its own, because `~/RoachNet` now holds an install. Move it back by hand:
  1. Quit RoachNet and RoachNet Setup, and don't run Homebrew until you're done. Don't open RoachNet again until step 5 has finished.
  2. Find the `~/RoachNet.backup-<time>` folder whose `storage` folder holds your Vault. It is usually the newest, the one with the largest number. Keep any other backups until you have checked them.
  3. Rename `~/RoachNet` to `~/RoachNet.empty`. Keep it until you have checked it: anything you made in RoachNet since that upgrade is in it.
  4. Rename the backup folder you found to `~/RoachNet`.
  5. Run 1.1.1's Setup again (Homebrew: `brew reinstall --cask roachnet`). The backup holds the older RoachNet app, which still has the download problem above; Setup replaces the app and keeps your storage.
  6. Open RoachNet.
- **Removal:** quit RoachNet, then remove `~/RoachNet/app` and `~/RoachNet/runtime`. Keep `~/RoachNet/storage` to keep your data. With Homebrew, `brew uninstall --cask roachnet` removes the Setup app; `brew uninstall --zap --cask roachnet` also moves all of `~/RoachNet`, your Vault included, to the Trash.
- **Folders beside the install:** `~/RoachNet.backup-…`, `~/RoachNet.setup-files-…` and `~/RoachNet.partial-restore-…` folders are left by Setup and may hold your data. Check them before you delete them.

## Known limitations

The same as 1.1.0. The download safeguards cover the names and links RoachNet is given; they don't defend against another program running as you that changes files in the storage folder while a download runs.

# RoachNet 1.1.1

Release date: not yet released
Version/build: 1.1.1 / 111
Platform: Apple Silicon Mac, macOS 14 or later
Installer: `RoachNet-Setup-macOS.dmg` (ad-hoc signed, not Apple-notarized — see "Opening the installer" below)
Companion: RoachNet-iOS 0.3.1 (unchanged, separate release)

RoachNet 1.1.1 is a security maintenance release for 1.1.0. It fixes one data-loss problem in downloads, adds two related download safeguards, and changes nothing else in the app. Everyone on 1.0.6, 1.0.7 or 1.1.0 should update.

## Security fix

**A malformed catalog download could delete RoachNet's storage folder.**

- **Severity:** High (preliminary): potential unintended local data deletion through malformed download descriptors. What it takes to trigger differs between the affected releases (below).
- **Affected versions:** RoachNet 1.0.6, 1.0.7 and 1.1.0 for macOS.
- **Not affected:** 1.0.5 and earlier, and the RoachNet iOS companion.
- **What happened:** when an entry in RoachNet's download catalog gave a file name that refers to a folder, RoachNet treated that folder as the download's file. When the download then failed, or when RoachNet moved the finished file into place, it removed that folder and everything in it.
  - For a knowledge (ZIM) download, that folder was the whole storage folder: the Vault, downloaded knowledge and maps, local models and RoachClaw's data.
  - Deleted files did not go to the Trash.
- **What it took:**
  - **1.0.7 and 1.1.0:** the download had to come from RoachNet's catalog address, and the catalog entry had to carry such a name. RoachNet's published catalog doesn't carry one. So this needed control over what the catalog serves.
  - **1.0.6:** it followed download descriptors from any web address, so starting a download from an untrusted link was enough.
- **What changed:**
  - A download whose name refers to a folder gets a generated name instead.
  - A download always lands directly inside its destination folder.
  - Cleanup removes only files, never a folder.
  - A failed, interrupted, cancelled or mismatched download leaves an existing file at its path in place.
  - Regression tests cover each case.

## Related download safeguards

Each keeps a download from writing into, or replacing, a file it doesn't own:

- A link at a download's partial file, symbolic or hard, is removed, never written through.
- One download writes a given file at a time, until its work has stopped, a cancelled one included. A second source for the same file is refused. Names that differ only in case or Unicode normalization count as one file.
- An install already running can't be cancelled halfway, and a collection queues each of its items on its own.

## Other changes

None. This release is 1.1.0 plus the fix and the safeguards above.

## Opening the installer

This build is **ad-hoc signed and not Apple-notarized**, like 1.1.0. On first launch macOS says RoachNet Setup cannot be verified: open System Settings › Privacy & Security and choose **Open Anyway** for RoachNet Setup. Verify the download first:

```sh
shasum -a 256 -c RoachNet-Setup-macOS.dmg.sha256
```

Homebrew: `brew tap --force RoachWares/roachnet && brew install --cask roachnet`

## Upgrade, rollback and removal

- **Before you update:** keep a current backup of `~/RoachNet/storage` (Time Machine works). Until you update, leave RoachNet's catalog address at its default and don't start downloads from links you don't trust.
- **Upgrade:** quit RoachNet and run Setup over the existing install. `~/RoachNet/storage` (Vault, settings, models) is kept.
- **Rollback:** 1.1.0 and 1.1.1 use the same storage format, but going back to 1.1.0 brings the problem back.
- **Removal:** quit RoachNet, then remove `~/RoachNet/app` and `~/RoachNet/runtime`. Keep `~/RoachNet/storage` to keep your data.
